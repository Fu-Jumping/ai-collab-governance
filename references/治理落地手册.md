# 治理落地手册（ai-collab-governance）

> 用途：L2/L3 档从零到稳定运转的落地方案：首月节奏、每周巡检、度量采集、评审操作、拦截记录。

## 1. 首月落地节奏（L2 标准档）

| 周 | 主题 | 动作 | 完成标志 |
| --- | --- | --- | --- |
| 第 1 周 | 立规矩 | AGENTS.md 入库（含 18 条协议）；三要素台账上线并补登存量任务；raw 留痕开始 | 第一个带出处的任务被认领；第一份 raw 落盘 |
| 第 2 周 | 跑红绿 | 挑一个中等任务全流程走九步执行流（含 `test:` 红 → `feat:` 绿）；评审人做一次完整的本地复跑演练 | 产出第一对红绿证据；执行流卡点修正 |
| 第 3 周 | 上门禁 | PR 模板启用；必跑矩阵进自检清单；有条件则配 CI（提交规范 + 构建测试） | 第一个按模板全量自检的 PR 合并 |
| 第 4 周 | 首次规则复盘 | 过一遍本月台账与事故；有事故走升级四步；无事故也演练写一条 R 编号规则 | 项目规则 §5 出现第一条有日期有教训的登记 |

**节奏原则**：每周只推一个主题——治理机制一次全上，团队会用脚投票绕过它。

## 2. 每周巡检清单（轮值，10 分钟）

- [ ] 任务台账：有没有超期"进行中"（>1 周无更新）？有没有无出处行？
- [ ] daily：最近 7 天逐日齐全？连续两天缺记录的成员优先对齐（**把记录缺失本身当风险信号**）。
- [ ] `test:` 提交抽查一个：diff 纯度 + 复跑红。
- [ ] 拦截记录：本周各层各拦了什么？（第 5 节表）
- [ ] R 台账：本周有没有该登记而没登记的教训？
- [ ] AI 失控信号：有没有解释不了的代码、没尾注的 AI 深度参与提交？

## 3. 度量采集实操（通用 git 命令，按月或里程碑出报告）

```bash
# AI 参与率
git log --since=... --grep="AI协作" --oneline | wc -l   # 除以总提交数

# 测试先行比例
git log --oneline | grep -c "^.*test:"      # 对比 feat: 数

# 提交类型分布
git log --pretty=%s | cut -d: -f1 | sort | uniq -c

# 人工打回次数（GitHub CLI）
gh pr list --state all --json reviews --limit 500 | grep -c CHANGES_REQUESTED
```

**结果解读警戒线**：

| 指标 | 警戒信号 |
| --- | --- |
| AI 参与率 | 快速上升而 raw 留痕量不动 → 过程失控前兆 |
| test:feat 比 | test 占比持续下降 → TDD 纪律松动的最早信号 |
| 打回次数 | 骤降为 0 且拦截记录也为空 → 不是没错误，是没人看 |
| 单人提交体量 | 平均行/次突然放大数倍 → 可能在合入未审的 AI 批量产出 |

## 4. AI 使用点五字段记录（示例）

```
任务：TODO-BE-023 订单状态机重构
类别：脚手架/样板代码
AI 做了什么：按已确认的状态图生成状态机骨架与单测脚手架（16 个文件）
人工审核与修改：删除 2 个 PRD 未定义的中间态；补充超时迁移的测试场景（AI 漏）
结果：部分采纳
```

要点：**"人工审核与修改"一栏永远要有内容**——如果连续多条都是"无修改"，要么是审核走过场（危险），要么是任务太简单（该自动化）。

## 5. 拦截记录表（L2 建议起用，L3 必用）

| 日期 | 拦截层（0~4） | 被拦下的东西 | 处置与结果 |
| --- | --- | --- | --- |
| {{…}} | 第 1 层 CI | `test:` 提交夹带 `types.ts` | 重写为 test→chore→feat 三段，diff 校验后推送 |

用途：① 证明"规则在工作"（用记录说话，不用"没出事"说话）；② 月度复盘看各层命中率——第 0/1 层命中多说明便宜，第 3/4 层命中多说明前面门禁有漏洞。

## 6. 评审人操作卡（五项必检的执行方式）

1. **提交序列纪律**：看 PR 的提交列表，`test:` 是否早于对应 `feat:`；
2. **红端复跑**：`git checkout <test提交>` → 跑测试 → **必须失败**，数字截图/记录；
3. **绿端复跑**：检出合并树 → 必跑矩阵 → **全绿**；
4. **diff 走查**：目录越界（改了不该改的板块）、口径残留（旧说法 grep）、禁区文件（daily 等）；
5. **证据核对**：PR 描述里的命令与结果，抽一条自己复现。
原则：**评审人不引用作者结论**——作者说绿不算绿，自己跑出来才算。

## 7. 常见落地失败模式

| 失败模式 | 根因 | 对策 |
| --- | --- | --- |
| 台账两周后没人更新 | 更新成本高于感知收益 | 砍字段回到三要素；把"证据列更新"绑进 PR 模板自检 |
| 红绿证据全是复制粘贴 | 评审不复跑 | 评审人本地复跑抽查（每周至少一次） |
| 规则台账变成垃圾场 | 什么小事都登记 | 只登记"事故驱动的规则"，好习惯不登记 |
| AI 尾注流于形式 | 没人看尾注数据 | 月度度量报告让数据被看见 |
| 全员大会宣布规则后无落地 | 规则没有承载物 | 每条规则必须落到"某个文件/某个检查项/某张表"之一 |
