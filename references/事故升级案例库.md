# 事故升级案例库（ai-collab-governance）

> 用途：起草规则补丁时，对照同类事故的升级写法。五个跨项目通用案例，均来自真实项目（已脱敏），每个按「事故 → 根因 → 规则升级 → 可验证条款」四段展开。
> 判断一条升级是否合格：**新规则能否被第三个人（或机器）在不询问起草者的情况下验证执行了没有。**

## 案例 1：测试提交夹带实现（假红绿）

- **事故**：PR 被打回。`test:` 提交里携带了全部业务实现，`feat:` 提交只有文档；在 `test:` 提交上复跑测试是**绿的**——"先红后绿"被字面满足，实质不成立。
- **根因**：原规则只约束"test: 早于 feat:"，不可验证的口号会被字面绕过（无论故意还是无意）。
- **规则升级**：TDD 纪律从"顺序要求"升格为"三条可验证条款"。
- **可验证条款**：① `test:` 提交 diff 只含测试文件与脚手架（CI 脚本可查）；② 在 `test:` 提交上复跑必须失败（评审人本地复跑）；③ 红绿两端数字写入 PR 描述。三者任一不满足即打回。

## 案例 2：多人同写日报撞车

- **事故**：两周内两次 PR 冲突（add/add），均为"成员在特性分支上起草当天 daily"与"汇总者维护 daily"两条通道并存所致。
- **根因**：单文件多人同写 + 特性分支必然与主分支撞车，是结构性冲突，不是操作失误。
- **规则升级**：两级留痕 + 写权分离。
- **可验证条款**：① 成员与 AI 只写 `docs/record/raw/` 自己的文件（同天同角色一个文件）；② `docs/record/daily/**` 唯一写权归次日汇总者；③ PR diff 含 `docs/record/daily/**` 即自动打回（CI 可查）。**制度设计消灭冲突源，而不是提醒大家小心。**

## 案例 3：只跑测试没跑构建

- **事故**：合并时只跑了 `npm test`（全绿），类型错误直到服务器构建才暴露，返工一次。
- **根因**："必跑测试"的门禁没有覆盖"构建+类型检查"这条腿。
- **规则升级**：按改动类型的必跑矩阵。
- **可验证条款**：改前端必须 `build`（含类型检查）**和** `test` 都过，命令与结果贴 PR 描述，缺项必须写理由——"没跑"是可检出状态，不再依赖自觉。

## 案例 4：mock 形状不一致掩盖真实缺陷

- **事故**：某功能 mock 模式完全正常、单测 E2E 全绿；接真实接口后换行与空格丢失、页面表现错误。同类问题当周再发两次（券名不更新、列表排序错）。
- **根因**：替身（mock）与真实后端行为不一致——mock 掩盖真实缺陷，且测试体系对这类差异天然免疫。
- **规则升级**：① mock 响应形状必须与契约逐字段一致的检查清单（字段名/类型/空值结构/错误码）；② "替身/真实不一致"单列为缺陷类；③ 真实接口联调不可省略，验收以真实链路为准。
- **可验证条款**：接业务逻辑前过 mock 形状清单（可对照打勾）；验收记录必须包含一次真实链路截图/日志。

## 案例 5：外部编辑器静默丢失内容

- **事故**：一份文档的全部批注"从未进入任何提交"——不是被删，而是外部编辑器保存回退导致静默丢失，团队事后用 `git log -S` 逐条比对才确认范围并恢复。
- **根因**：编辑工具绕过版本控制且失败静默。
- **规则升级**：① 关键文档编辑期禁用外部编辑器保存同一文件；② 每轮改动用显式路径提交（顺手就有了 diff 证据）；③ 敏感批量操作前先备份 + 校验和比对。
- **可验证条款**：批量操作前存在备份目录与校验记录；提交记录可复现每轮改动范围。

## 升级流程回顾（四步，配合空白复盘单使用）

1. **落缺陷单**（含根因，不止现象）；
2. **起草规则补丁**：先回答"旧规则为什么没拦住"——缺失？不可验证？没人知道？
3. **写成可验证条款**：能进 CI 的进 CI，能进 PR 检查项的进检查项，能复跑的写进评审清单；
4. **登记长期约束台账**：追加式编号（R1、R2…），注明日期与教训来源；历史条目原样保留，未采纳的提案也留痕——**规则演进史本身是治理的证据**。
